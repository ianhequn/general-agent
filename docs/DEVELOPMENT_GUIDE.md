# 开发与仓库管理规范

## 1. 管理目标

本仓库需要同时保持三件事：

1. 初学者可以按顺序理解 Agent 的演化。
2. 每个已发布阶段可以独立运行和验证。
3. 最终产品可以持续升级，而不受教学快照结构限制。

因此采用“编号教程目录 + 独立产品源码”的双线管理方式。

## 2. 预期目录

```text
general-agent/
|-- readme.md
|-- docs/
|   |-- ROADMAP.md
|   |-- DEVELOPMENT_GUIDE.md
|   `-- architecture.md          # Agent Core 稳定后补充
|-- 01-minimal-agent/
|-- 02-tool-calling-agent/
|-- 03-agent-core/
|-- ...
|-- src/
|   `-- mycodex/                 # 第 03 阶段后建立的产品代码
|-- tests/                       # 产品级测试
|-- examples/                    # 产品级演示任务
|-- pyproject.toml               # 产品依赖、CLI 入口和工具配置
|-- CHANGELOG.md
|-- CONTRIBUTING.md
`-- LICENSE
```

这里只定义预期结构，不提前创建空目录。文件在对应阶段真正需要时再加入。

## 3. 教程阶段目录规范

每个编号目录使用 `NN-topic-name` 命名，并至少包含：

```text
NN-topic-name/
|-- README.md              # 本章目标、原理、运行方法和限制
|-- agent.py               # 可直接运行的最小入口
|-- requirements.txt       # 本章的最小依赖
|-- tests/                 # 不调用真实模型 API 的测试
`-- example_project/       # 可复现的最小任务
```

如果一章只有一个简单模块，可以暂时保持单文件。只有当出现独立职责或必须单测的边界时才拆分，
例如 `tools.py`、`model_client.py`、`trajectory.py`。

## 4. 代码职责边界

最终 Agent 的依赖方向保持为：

```text
CLI
 -> Agent Loop
     -> Model Client
     -> Tool Registry -> Tool Implementations -> OS / Workspace
     -> Trajectory Recorder
```

- CLI 只负责读取参数、加载配置和展示结果。
- Agent Loop 只负责状态推进，不直接操作文件或启动进程。
- Model Client 只负责 API 请求与响应转换，不执行工具。
- Tool Registry 负责工具声明、参数校验和路由。
- Tool Implementation 负责真实副作用，并返回统一结构。
- Trajectory Recorder 负责脱敏、序列化和持久化，不决定 Agent 行为。

禁止让工具反向调用模型，也不要让 API SDK 对象直接散落到整个代码库。

## 5. 实现规则

- 所有可执行入口放入 `main()`，并使用 `if __name__ == "__main__":`，保证模块可导入测试。
- 配置通过命令行参数、配置对象或环境变量注入，不把任务、模型和绝对路径硬编码在核心逻辑中。
- API Key 只从环境变量读取，日志和轨迹必须脱敏。
- 模型输出始终视为不可信输入；工具名、JSON 参数、路径和数值都需要校验。
- 工具结果使用稳定的字典结构，至少包含成功状态和错误信息；命令工具额外记录返回码与超时状态。
- `max_calls` 统计模型 API 调用次数；工具调用次数单独记录，避免指标含义变化。
- 多工具调用先按顺序执行，等单线程行为稳定并有测试后再考虑并发。
- 固定工作目录只是执行起点，不是安全隔离。Sandbox 完成前必须在文档中保留风险提示。

## 6. 测试规则

测试分三层：

| 层级 | 验证内容 | 是否调用真实 API |
| --- | --- | --- |
| 单元测试 | 参数校验、工具路由、超时、序列化 | 否 |
| Agent Loop 测试 | 使用 fake/mock 模型响应推进完整状态 | 否 |
| 手动烟雾测试 | 使用真实模型完成 `example_project` | 是 |

每次提交至少运行本阶段测试。使用真实 API 的测试不能作为默认测试，避免产生费用和不稳定结果。

每个阶段的验收记录应包含运行命令、预期结果和已知限制。需要保存轨迹示例时，先移除 API Key、
用户名、绝对路径和私人仓库内容。

## 7. Git 与版本管理

- `main` 始终保持可运行；实验性改动使用独立分支。
- 一次提交只表达一个主要变化，推荐格式为 `type(scope): summary`。
- 教程提交示例：`feat(stage-02): add native tool calling`。
- 修复提交示例：`fix(stage-01): handle command timeout`。
- 文档提交示例：`docs: define project roadmap`。
- 每个教程阶段完成后创建 `stage-NN-complete` 标签。
- 产品建立后使用语义化版本，例如 `v0.1.0`；教程阶段编号不与产品版本号混用。

不要提交以下内容：

- `.env`、API Key 或访问令牌。
- 未脱敏的 `trajectory.json`。
- 虚拟环境、缓存和编辑器配置。
- 只在个人电脑上有效的绝对路径。
- 无法说明来源或许可证的第三方代码与资源。

## 8. 文档状态规则

文档必须明确区分：

- **已完成**：代码存在，并通过约定验证。
- **进行中**：代码正在开发，接口可能变化。
- **计划中**：只有路线和目标，不能写成仓库已经具备的能力。

每次阶段完成时同步更新三处内容：根 README 的当前进度、本阶段 README 的运行说明、
`ROADMAP.md` 的完成状态。代码变化但文档没有同步，不算阶段完成。

## 9. 新阶段工作流

1. 写清本阶段只解决的一个核心问题和完成标准。
2. 建立最小示例或失败测试，确认问题可以被观察。
3. 完成最小可运行实现，不提前加入后续能力。
4. 使用 mock 测试核心流程，再做一次真实 API 烟雾测试。
5. 补齐原理、消息流、运行命令、预期输出和限制。
6. 更新路线状态，检查敏感信息，然后合并到 `main`。

## 10. 当前阶段约束

`01-minimal-agent` 当前包含已完成的 v0/v0.5 和正在开发的 v1。为了保留开发连续性，
v1 可以先在该目录完成；当 Function Calling 通过测试后，再将完成版本整理为独立的
`02-tool-calling-agent` 教程快照。

当前新增的 `tools.py` 属于用户手写练习文件。修改它时优先解释接口和执行链路，而不是直接代写，
除非仓库维护者明确要求自动实现。
