# 从 SWE Agent 到自己的 Codex

## 路线目标

本路线不是复刻某个商业产品的内部实现，而是从公开、可解释的工程组件出发，
构建一个能够理解任务、检查仓库、修改代码、运行验证并汇报结果的 Coding Agent。

学习线负责回答“它为什么这样工作”，产品线最终回答“它能否稳定地被别人使用”。

## 阶段路线

| 章节 | 核心问题 | 最小交付 | 完成标准 |
| --- | --- | --- | --- |
| 01 最小 Agent | 模型如何通过 observation 连续行动？ | 单 Agent Loop、命令执行、轨迹记录 | 能完成一个最小修复任务并正常退出 |
| 02 Tool Calling | 如何摆脱脆弱的文本正则协议？ | 工具 Schema、参数校验、工具结果回传 | 能处理成功、失败、超时和非法调用 |
| 03 Agent Core | 如何让循环可配置、可测试、可复用？ | 配置对象、模型客户端、Agent 状态与结果 | 不调用真实 API 也能测试完整循环 |
| 04 代码工具 | 如何可靠地读取、搜索和修改仓库？ | 文件读取、搜索、补丁编辑、测试工具 | 修改范围可追踪，工具返回结构统一 |
| 05 Plan Mode | 如何先规划再执行，并知道任务做到哪一步？ | 计划、步骤状态、完成条件 | 能展示计划并按状态推进或停止 |
| 06 Sandbox | 如何限制命令、路径、时间和资源？ | 隔离执行环境、权限策略、危险操作拦截 | 恶意示例不能逃离允许的工作区 |
| 07 Sub-agent | 什么任务值得委派，结果如何汇总？ | 子任务协议、上下文裁剪、结果合并 | 并行或委派不会破坏主任务状态 |
| 08 Memory | 哪些信息应该跨轮次或跨会话保留？ | 短期摘要、项目记忆、恢复机制 | 能恢复任务且不会把无关历史无限累积 |
| 09 Evals | 如何证明升级真的更好？ | 固定任务集、成功率、成本和步数统计 | 每次关键改动都有可比较的评测结果 |
| 10 产品化 | 如何让普通开发者安装并使用？ | `mycodex` CLI/TUI、配置、日志、发布包 | 新用户能按文档安装并完成真实仓库任务 |

## 两条代码线

### 教程阶段

编号目录是可运行的学习快照，例如 `01-minimal-agent/`、
`02-tool-calling-agent/`。每个目录只突出一个新的核心概念，避免读者一开始就面对完整产品的复杂度。

一个阶段完成后原则上冻结。后续只修复安全问题、运行错误或明显误导读者的文档，
不把未来章节的架构整体反向移植。

### 最终产品

当第 03 阶段的 Agent Core 接口稳定后，建立 `src/mycodex/`。后续已经验证的能力进入产品线，
并补充配置、兼容性、错误处理、日志和用户体验。教程目录展示演化过程，产品目录维护最新实现。

## 近期里程碑

### v1：原生 Tool Calling

- 定义 `run_command` 和 `finish_task` 两个最小工具。
- 将模型返回的 `tool_calls` 路由到本地实现。
- 使用 `role="tool"` 和 `tool_call_id` 回传结构化结果。
- 覆盖命令成功、非零返回、超时、非法 JSON、未知工具和调用上限。
- 使用 mock 响应测试 Agent Loop，不消耗真实 API。

### v1 完成后

不要立刻增加 Sub-agent。下一步先把 Agent Loop 拆成可注入的模型客户端、工具注册表和轨迹记录器，
使同一套测试可以稳定验证之后的每次升级。

## 最终产品定义

最终产品暂用包名 `mycodex`，目标用户是希望在本地仓库中使用可解释 Coding Agent 的开发者。
第一版产品至少应做到：

- 接受自然语言任务和工作区路径。
- 检查、搜索、修改代码并运行测试。
- 在执行前展示关键计划，在危险操作前进行权限控制。
- 保存可脱敏、可复盘的任务轨迹。
- 能从中断处恢复，并能报告成功、失败或阻塞原因。
- 提供明确安装命令、配置说明和跨平台支持范围。

不以“工具数量多”作为完成标准。稳定完成真实任务、行为可解释、权限边界清楚，才是产品价值。
